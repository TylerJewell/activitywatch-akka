# Benchmark — port against source system

Measured 2026-08-19, on one machine, against `ActivityWatch/activitywatch` at the tip of
`master` — `aw-core` 0.5.17, `aw-server`, `aw-client` and `aw-watcher-afk`, installed into
`.venv-aw`.
Source runtime: Python 3.12.14 · Port runtime: Java 25.0.2.

Everything here comes from `bench/compare.py`, which runs the original in its own process
and the port through `PortBenchmarkTest` over the same `bench/workload.json`, and from
`toolkit/loc.py` and `toolkit/slice_loc.py`. Nothing is transcribed from a previous run;
`bench/results.json` is what that run wrote.

The workload: 5,000 window heartbeats arriving in order, 2,000 readings of "seconds since
last input", and an activity query over 2,000 window events and 200 idle events.

---

## 1. Same answers first

### 1.1 Where the port copies the source

| Behaviour | Cases | Agree |
|---|---:|---:|
| Merge or insert, decided per heartbeat | 5,000 | **5,000 of 5,000** |
| The bucket left behind, event by event | 648 | **648 of 648** |
| The heartbeats the idle rule sends | 2,000 | **2,000 of 2,000** |
| Window events after flooding | 1,944 | **1,944 of 1,944** |
| The activities, longest first | 5 | **5 of 5** |

Both sides are the real thing. The original's figures come from `aw_server.api.ServerAPI`,
from `aw_watcher_afk.afk.AFKWatcher.heartbeat_loop` driven over the scripted readings, and
from `aw_transform`'s own functions. The port's come from `Heartbeats`, `BucketState`,
`IdleRule`, `Flood` and `Activities`. Timestamps are compared to the millisecond and
durations to the millisecond, which is the resolution the original stores.

A separate 27-case corpus, generated by `probes/probe_05_corpus.py` from the same
installation, is what the port's own test suite checks against; `probe_05_corpus.py
--check` regenerates it and fails if the original has moved. The five rows above are a
second, larger comparison run fresh at benchmark time, so a stale corpus could not produce
them.

**On this workload the original's two storage backends agree with each other**, which is
what makes row two a comparison against one answer rather than two. That is not true in
general, and §1.2 is the case where it is not.

### 1.2 Where there is no single answer to copy

Three short streams in which a heartbeat arrives out of order. Each was run through the
original on both storage backends it ships, and through the port. The decision sequence —
merge or insert, per heartbeat — is **identical across all three in every case**. What
differs is which stored event the merge rewrites, and there the original disagrees with
itself.

**A heartbeat one second late** — heartbeats at 22 s, 21 s, 23 s, all the same data:

| | Bucket left behind |
|---|---|
| Original, in-memory backend | `21 s +0 s`, `21 s +2 s` |
| Original, SQLite backend | `21 s +2 s`, `21 s +0 s` |
| **This port** | `22 s +0 s`, `21 s +2 s` |

Both backends lost the event at 22 s. They also return the two survivors in opposite
orders. The port keeps all three heartbeats' worth of history: the event at 22 s that
nothing merged into, and the one at 21 s that the heartbeat at 23 s lengthened by 2 s.

**Returning from idle, then two polls with no fresh input** — the sequence a real AFK
watcher sends, from `probes/probe_03_idle_rule.py`:

| | Bucket left behind |
|---|---|
| Original, in-memory backend | `30 s +15 s not-afk`, `30 s +0 s not-afk`, `0.001 s +30 s afk`, `0 s +0 s not-afk` |
| Original, SQLite backend | `30 s +15 s not-afk`, `30 s +0 s not-afk`, `30 s +0 s not-afk`, `0 s +0 s not-afk` |
| **This port** | `30.001 s +0 s not-afk`, `30 s +15 s not-afk`, `0.001 s +30 s afk`, `0 s +0 s not-afk` |

On SQLite the thirty-second idle stretch is gone — overwritten by an active event. On the
in-memory backend it survives but the active event that opened at 30.001 s does not. The
port keeps both.

**A heartbeat matching an event two back** — `a` at 0 s for 4 s, `b` at 20 s, then `a`
again at 1 s and 3 s:

| | Bucket left behind |
|---|---|
| Original, in-memory backend | `1 s +0 s a`, `1 s +2 s a`, `0 s +4 s a` |
| Original, SQLite backend | `0 s +4 s a`, `1 s +2 s a`, `1 s +0 s a` |
| **This port** | `20 s +0 s b`, `1 s +2 s a`, `0 s +4 s a` |

Both backends destroyed the `b` event entirely — the only record that a different
application was in front of the user at 20 s. Neither is a bug being reported here: the
original's merge does not name the event it merged, so each backend has to guess, and the
two guess differently. The port names it. `SPEC-001` §4 OD-1 is where that decision is
written down, and the README lists it as a difference.

## 2. Speed

Only because §1.1 agrees. Median of five runs after a warm-up; every figure is nanoseconds
for one operation, measured in-process with no network on either side.

| Operation | Original | This port | Port is |
|---|---:|---:|---:|
| Decide whether one heartbeat merges | 1,356 ns | 247 ns | **5.5× faster** |
| Take one heartbeat all the way into a bucket | 73,472 ns | 1,635 ns | **44.9× faster** |
| Apply the idle rule to one reading | 3,708 ns | 311 ns | **11.9× faster** |
| Run the whole activity query once | 35.3 ms | 3.0 ms | **11.6× faster** |

Rows one, three and four are like for like: the same computation on the same inputs, with
nothing stored and nothing sent. A 5–12× difference between compiled Java and interpreted
Python on arithmetic over timestamps is unremarkable, and it is quoted because it is what
was measured, not because it is interesting.

**Row two is not like for like, and 44.9 is not a claim that the port ingests forty-five
times faster.** The two sides do different amounts of work per heartbeat:

- The original does the merge decision and then writes through its datastore layer. On the
  in-memory backend, rewriting the last event sorts the whole bucket to find which row that
  is — so the cost of one heartbeat grows with the number of events already in the bucket.
- The port does the merge decision and rebuilds its bucket record. Its cost also grows with
  the bucket, because the record is copied on every write, but it copies rather than sorts.

Both are super-linear in the size of the bucket, and 5,000 heartbeats is where these two
particular curves happen to sit. What is missing from the port's 1,635 ns is everything the
Akka runtime does around the decision — writing the event to a journal, replicating it,
handing it to a view. Those are real and they are not in this number.

**The port's per-heartbeat cost is dominated by copying, and that has been left alone.** A
bucket keeps up to 2,000 events and copies that list on every write. At one heartbeat every
five seconds per watcher, 1.6 µs of copying is not a cost anyone can observe, and removing
it would mean a persistent data structure inside entity state to solve a problem nothing
has.

### 3.3 Attributed reduction

Quoted only where the cause can be named. Two causes account for whole files inside the
1,278 counted above:

| Cause | Source lines that go |
|---|---:|
| No pluggable storage. The original has an abstract storage interface with three implementations behind it, chosen at startup; the port's events live in one place and there is nothing to choose. | 79 |
| No datastore layer between the decision and the events. The original's `Datastore`/`Bucket` pair exists to give three different backends one shape; the port's bucket holds its own events. | 136 |
| **Total, inside the slice** | **215** |

So the part genuinely rebuilt is 1,278 − 215 = **1,063 source lines against 940 port lines,
a ratio of 1.13:1** — and that is the honest headline. A port of this slice is not
meaningfully smaller than the thing it is a port of. Where lines went is not where they
came back: the port spends more on being explicit about the decisions in §1.2 and less on
having three ways to store an event.

A third cause is real and is deliberately **not** subtracted, because it was never inside
the 1,278: `aw_query`, the small language the web interface sends to the server and the
server interprets, is 630 lines in `aw-core/aw_query`. The port calls the pipeline directly
and has no language. Counting those 630 would compare this port against a slice larger than
the one measured.

## 4. What this does and does not show

**It shows** that the port answers exactly as ActivityWatch does everywhere it claims to
copy it — 5,000 merge decisions, a 648-event bucket, 2,000 idle heartbeats, 1,944 flooded
events and 5 activities, run rather than read, on inputs neither side's tests were written
against.

**It shows** that where the original has no single answer, it really has none: its two
shipped storage backends leave different buckets from identical heartbeats, and in two of
the three cases each loses an event the other keeps. The port's choice is written down in
`SPEC-001` §4 OD-1 rather than left to whichever backend is configured.

**It does not show** that the port is faster in any way a user of either system would feel.
Watchers send a heartbeat every few seconds. Nothing here is the bottleneck in either
system, and the largest ratio in §2 is the row that is least like for like.

**It does not measure the Akka runtime.** Every port figure is the decision work with the
runtime taken out: no journal write, no replication, no view update. Those are what a
deployed port would actually spend its time on, and none of them appear here. The nine
integration tests start the real runtime and check behaviour, not speed.

**It does not measure the original's real deployment either.** A running ActivityWatch
stores to SQLite on disk and receives heartbeats over HTTP from separate watcher processes.
The in-memory backend was used here so that the comparison is of two decision paths rather
than of a disk and a network.

**It does not cover the parts of the original left out of the slice** — the query language,
categorisation, browser events, the Android watcher, export and import. §3.1 exists to
refuse the ratio that would come from pretending otherwise.

**The size comparison is not a claim of simplicity.** At 1.13:1 on the part genuinely
rebuilt, the two are about the same size. The 1.4:1 in §3.2 counts a storage abstraction
the port replaces with nothing.
